# GitHub Actions ハンズオン手順書

**GitHub Actions Training（全 2 日）受講者用**

---

## この手順書について

このワークショップでは、**3 回のハンズオン**を行います。
このファイルは、その **すべての操作手順とコピー用のコード** をまとめたものです。

> **当日は、この手順書を手元に開いたまま参加してください。**
> 講師の画面と、みなさんが操作する画面は別の端末になります。
> 講師が 1 手ずつ実演しますが、**手順の文字情報はこの手順書にしかありません**。

> 💡 **この手順書は、研修用リポジトリの中にも入っています。**
> `docs/handson-guide.md` を開けば、**操作する端末のブラウザ上でそのまま読めます。**
> コードのコピー＆ペーストが同じ画面の中でできるので、**そちらをおすすめします。**

### 3 回のハンズオンの全体像

| # | 日程 | 内容 | 所要 | この手順書の章 |
|---|---|---|---|---|
| ① | Day 1 | はじめてのワークフローを作って動かす | 15 分 | 第 1 章 |
| ② | Day 1 | わざと壊して、ログを読んで直す | 10 分 | 第 2 章 |
| ③ | Day 2 | PR で自動テストが走る形にする | 15 分 | 第 3 章 |

**3 回とも、同じ 1 つのファイルを育てていきます。**
リポジトリを行き来したり、新しいファイルを作り直したりはしません。

### 必要なもの

- **Web ブラウザだけ**です。Git のインストールも、コマンドラインも使いません。
- 会社の GitHub アカウントでログインできること。
- **研修用リポジトリ**にアクセスできること（管理者の方が用意してくださいます）。

> **事前にインストールしていただくものは、一切ありません。**
> リポジトリの取得（clone）も、パッケージのダウンロードも不要です。
> 演習の処理は、すべてサーバー側で実行されます。みなさんの端末では何も動きません。

### 👥 全員で 1 つのリポジトリを使います

本日は、**管理者の方が用意した研修用リポジトリ 1 つ**を全員で使います。
ただし、作業する場所（**ブランチ**）は 1 人ずつ分かれています。

| | |
|---|---|
| **リポジトリ** | 全員共通（当日ご案内します） |
| **自分の作業場所** | `exercise/自分の GitHub ユーザー名` というブランチ |

**作り方は第 0 章で説明します。**
自分のブランチの中で何をしても、他の方には影響しません。

### 🖥 本日の実行環境（`runs-on`）

ワークフローには **「どのマシンで実行するか」** を書く行が必ずあります。それが `runs-on:` です。

| | 値 |
|---|---|
| **本日使う値** | `[self-hosted, Windows]` |

> ⚠️ **貼り付けたコードの `runs-on:` の行は、書き換えずにそのまま使ってください。**
> この手順書に載っているコードは、すべて本日の環境に合わせた状態になっています。
>
> `runs-on:` に何を書けるかは、みなさんの会社の GitHub 環境によって変わります。
> **講師が当日あらためてご案内します。**

### ⏳ 実行は「順番待ち」になります

本日の環境では、**同時に実行できるワークフローは 1 つ**です。

そのため、みなさんが一斉にコミットすると、実行はすぐには始まらず、
**灰色の丸（待機中）のまま順番待ちの列に並びます。**

| 表示 | 意味 |
|---|---|
| ⚪ 灰色の丸 | 順番待ちです。**故障ではありません** |
| 🟡 黄色の丸 | 自分の番が来て、いま動いています |
| 🟢 緑のチェック | 成功しました |
| 🔴 赤のバツ | 失敗しました（ログを読んで直します） |

> **待っている間は、ページを何度も再読み込みしなくて大丈夫です。**
> 数分待っても灰色のままでも、正常です。
>
> なお、この「実行が重なったときにどう捌くか」という話は、
> **Day 2 の `concurrency`** でそのまま扱います。
> 待ち時間そのものが、今日の教材の一部だとお考えください。

### うまくいかなかったときは

- **できなくても、次に進めます。** 各ハンズオンの最後に「完成形のコード」を載せてあります。
- 講師からはみなさんの画面が見えません。**詰まったら遠慮なく声を上げてください。**
  必要ならカメラで画面を映していただくか、チャットにエラーメッセージを貼ってください。
- 詰まった状態が続いても大丈夫です。付録 A に **Day 1 終了時点の完成形** を載せてあるので、
  Day 2 はそこから再開できます。

## 第 1 章 ハンズオン① はじめてのワークフロー

**Day 1 / 所要 15 分**

### この章のゴール

- `.github/workflows/ci.yml` というファイルを作る
- コードを push したら、GitHub 上で自動的に何かが動くのを体験する
- 実行ログを自分で開いて読む

### なぜこれをやるのか

GitHub Actions は、**「リポジトリで何かが起きたら、GitHub のサーバー上で決めた処理を自動で走らせる」** 仕組みです。

その「決めた処理」を書いたファイルが **ワークフローファイル** で、
置き場所は **`.github/workflows/` の中**と決まっています。
この場所に置くだけで、GitHub が勝手に見つけて動かしてくれます。

まずは、いちばん単純な「文字を出すだけ」のワークフローを作ってみます。

---

### 手順 1-1 ファイルを新規作成する

> ⚠️ **始める前に、左上のボタンが `exercise/自分の名前` になっていることを確認してください。**
> `main` になっていたら、ボタンを押して自分のブランチに切り替えてください。

**1.** リポジトリのトップ画面（`Code` タブ）を開きます。

**2.** ファイル一覧の右上あたりにある **`Add file`** ボタンをクリックし、
　　メニューから **`+ Create new file`** を選びます。

**3.** 画面上部に、ファイル名を入れる欄が出ます。
　　ここに **次の文字列をそのまま入力してください。**

```
.github/workflows/ci.yml
```

> **入力のコツ**
> `/`（スラッシュ）を打つたびに、入力欄が自動的に区切られてフォルダとして扱われます。
> これは正常な動きです。そのまま最後まで打ち切ってください。
>
> 打ち終わったとき、画面に `.github` `/` `workflows` `/` `ci.yml` のように
> 分かれて表示されていれば成功です。

> ⚠️ **よくある間違い**
> - `.github` の先頭のドット（`.`）を忘れる
> - `workflows` を `workflow`（単数形）にしてしまう
> - `.yml` を `.yaml` にする → これは **どちらでも動きます**。気にしないでください。

---

### 手順 1-2 コードを貼り付ける

ファイル名の下に、大きな入力欄（エディタ）があります。
そこに **以下をそのままコピーして貼り付けてください。**

> 💡 **同じ内容が `snippets/01-first-workflow.yml` にも入っています。**
> リポジトリでそのファイルを開き、右上の**コピーボタン**を押すのがいちばん確実です。

```yaml
name: CI

on:
  push:

jobs:
  hello:
    runs-on: [self-hosted, Windows]
    steps:
      - uses: actions/checkout@v5
      - name: あいさつを表示する
        run: echo "Hello GitHub Actions"
      - run: ls
```

> ⚠️ **貼り付けたあと、必ず確認してください**
> YAML は **字下げ（インデント）に意味がある** 言語です。
> 貼り付けたときに字下げが崩れていないか、目視で確認してください。
> 崩れていたら、一度全部消して貼り直すのが確実です。
>
> 詳しくは **付録 B「YAML の落とし穴」** を参照してください。

#### このコードが何をしているか

| 行 | 意味 |
|---|---|
| `name: CI` | このワークフローの表示名。Actions タブにこの名前で並びます |
| `on:` | **いつ動かすか**。ここでは `push:` なので「コードが push されたとき」 |
| `jobs:` | **何をするか**の入れ物。この下にジョブを並べます |
| `hello:` | ジョブの名前。自由に付けられます |
| `runs-on:` | **どこで動かすか**。ワークフローを実行するマシンの指定です（本日の値は冒頭の「本日の実行環境」を参照） |
| `steps:` | ジョブの中で、上から順に実行される処理のリスト |
| `- uses: actions/checkout@v5` | **リポジトリのコードを実行環境に持ってくる**（詳しくは第 2 章で） |
| `- run: echo "..."` | シェルコマンドをそのまま実行する |
| `- run: ls` | ファイル一覧を表示する |

---

### 手順 1-3 コミットする

**1.** エディタの右上（または画面下部）にある **`Commit changes...`** ボタンを押します。

**2.** ダイアログが開きます。次のように設定します。

| 項目 | 設定 |
|---|---|
| **Commit message** | `add first workflow`（何でも構いません） |
| **Extended description** | 空欄のまま |
| **選択肢** | **上の選択肢**（`Commit directly to the exercise/... branch`）← 重要 |

> ⚠️ **選択肢に自分のブランチ名が出ているか確認してください。**
>
> | 表示 | 対応 |
> |---|---|
> | `Commit directly to the exercise/自分の名前 branch` | ✅ そのまま進む |
> | `Commit directly to the main branch` | ❌ **押さないでください。**第 0 章 手順 0-2 へ |
>
> **`Create a new branch...`（下の選択肢）も選ばないでください。**
> 自分のブランチは第 0 章でもう作ってあります。

**3.** **`Commit changes`** ボタンを押します。

---

### 手順 1-4 動いたのを確認する

> 📌 **本日は全員が同じリポジトリを使っています。**
> `Actions` タブには**他の方の実行も一緒に並びます。**
> **自分の実行を確実に開く方法**を、先に覚えてしまいましょう。

#### ★ いちばん簡単な方法（おすすめ）

**1.** `Code` タブを開きます（左上のボタンは自分のブランチのまま）。

**2.** ファイル一覧の**すぐ上**に、自分の最新コミットが表示されています。
　　その右側に **状態のマーク（⚪ 🟡 ✅ ❌）** が出ています。

**3.** **そのマークをクリック**します。→ 自分の実行に直接飛べます。

#### 別の方法（`Actions` タブから探す）

**1.** 画面上部の **`Actions`** タブをクリックします。

**2.** 左側の一覧から **`CI`** をクリックします。

**3.** 一覧の上にある **`Branch`**（ブランチ）の絞り込みを押し、
　　**自分のブランチ名**を選びます。

これで**自分の実行だけ**が表示されます。

---

**4.** 状態のマークを見てください。

| マーク | 意味 |
|---|---|
| ⚪ 灰色の丸 | **順番待ち**（まだ始まっていない） |
| 🟡 黄色い丸（くるくる回る） | いま実行中 |
| ✅ 緑のチェック | 成功 |
| ❌ 赤いバツ | 失敗 |

> **灰色や黄色のまま数分かかることがあります。** これは正常です。
> 本日の環境では、実行できるワークフローが**同時に 1 つ**のため、
> 他の方の実行が終わるまで順番を待ちます。
> **何度も再読み込みする必要はありません。**

**5.** 実行の行（`add first workflow` などのコミットメッセージ）をクリックします。

**6.** 左側に **`hello`** というジョブ名が出ます。これをクリックします。

**7.** 右側にステップが縦に並びます。それぞれの行をクリックすると、**ログが開きます。**

---

### ✅ ハンズオン① 完了チェック

次の 3 つが確認できたら成功です。

- [ ] **実行された** — 自分のブランチの実行があり、緑のチェックになっている
- [ ] **ログが読める** — `hello` ジョブを開き、各ステップのログが展開できる
- [ ] **内容が正しい** — 「あいさつを表示する」のステップに `Hello GitHub Actions` が出ている
- [ ] （おまけ）`ls` のステップに `README.md` が含まれている

---

### 💡 もし失敗していたら

| ログに出ているもの | 原因と対処 |
|---|---|
| Actions タブに何も出ない | ファイルのパスが違います。`.github/workflows/ci.yml` を確認 |
| 赤いバツ、`Invalid workflow file` | YAML の字下げが崩れています。付録 B を参照して貼り直し |
| 赤いバツ、`could not find any workflows` | ファイル名が `.yml` / `.yaml` 以外になっています |

**それでも直らないときは、ファイルを一度削除して、手順 1-1 からやり直すのが確実です。**

## 第 2 章 ハンズオン② わざと壊して、直す

**Day 1 / 所要 10 分**

### この章のゴール

- ワークフローを**わざと失敗させる**
- 失敗したログを開いて、**エラーメッセージを読む**
- **自分で直す**

### なぜこれをやるのか

CI を導入すると、**失敗は毎日起きます。**
そのとき「なぜ失敗したのか」を自分で読み解けるかどうかが、いちばん大事なスキルです。

ここでは、**最もよく起きる失敗のひとつ**をわざと再現します。

---

### 手順 2-1 1 行だけ消す

**1.** `Code` タブ → `.github` → `workflows` → `ci.yml` の順にクリックして、
　　第 1 章で作ったファイルを開きます。

**2.** 右上の **鉛筆マーク（✏️ Edit this file）** をクリックします。

**3.** 中身を、以下の内容に**まるごと貼り替えます。**
　　（`snippets/02-broken.yml` に同じものが入っています）

　　第 1 章のコードとの違いは 2 つです。
　　- `- uses: actions/checkout@v5` の行が **無くなっている**
　　- `- run: ls` が `- run: cat README.md` に**変わっている**

```yaml
name: CI

on:
  push:

jobs:
  hello:
    runs-on: [self-hosted, Windows]
    steps:
      - name: 作業フォルダを空にする
        run: |
          Get-ChildItem -Force |
            Remove-Item -Recurse -Force -ErrorAction Ignore

      - run: cat README.md
      - run: echo "done"
```

> 💡 **いちばん上のステップは何をしているの？**
>
> 皆さまが使うランナーは**自社のマシン**なので、前回の実行で使ったフォルダを
> **そのまま使い回します。** 何もしないと「前回の残りファイル」が見えてしまい、
> この演習が成立しません。
> そこで、最初に作業フォルダを空にしています。
> **演習を確実に再現するための準備**だと思ってください。理由は手順 2-4 で説明します。

**4.** `Commit changes...` → **上の選択肢**（`Commit directly to the exercise/... branch`）
　　を選んでコミットします。

> ⚠️ 選択肢に**自分のブランチ名**が出ていることを確認してください。
> `main` になっていたら、第 0 章 手順 0-2 に戻ってください。

---

### 手順 2-2 失敗を見る

**1.** `Code` タブのコミット横の**状態マーク**をクリックします。
　　（`Actions` タブから探す場合は、`Branch` の絞り込みで自分のブランチを選びます）

**2.** 新しい実行が始まります。しばらく待つと **❌ 赤いバツ** になります。

**3.** その実行をクリックし、`hello` ジョブを開き、**赤くなっているステップ**をクリックします。

**4.** ログに、次のようなメッセージが出ているはずです。

```
cat : Cannot find path 'C:\actions-runner\_work\...\README.md' because it does not exist.
    + FullyQualifiedErrorId : PathNotFound,Microsoft.PowerShell.Commands.GetContentCommand
Error: Process completed with exit code 1.
```

> 文言は環境によって多少変わりますが、
> **`Cannot find path`（そんな場所にファイルは無い）** と出ていれば同じことです。

---

`Code` タブを見れば、そこにあります。

**それなのに、なぜ「そんなファイルはない」と言われるのでしょうか？**

<summary>ヒント 1（クリックで開きます）</summary>

ステップは、**上から順に**実行されます。
このワークフローには、いま 2 つのステップしかありません。
</details>

<details>
<summary>ヒント 2</summary>

`runs-on:` は、**ワークフローを実行するマシンを指定する**行です。

</details>

</details>

### 手順 2-4 直す

**答え：`actions/checkout` のステップが無いからです。**

`runs-on:` で指定したマシンに、リポジトリのコードは**自動では置かれません。**

`actions/checkout` は、**「このリポジトリのコードを、実行環境の中に持ってくる」** ための
GitHub 公式の部品（Action）です。

> **覚えておいてください**
> ファイルを触るワークフローには、**ほぼ必ず `actions/checkout` が要ります。**
> これは Actions を書き始めたときの、最頻出のつまずきポイントです。

> 📌 **実行環境には 2 種類あります**
>
> | | GitHub ホステッド | セルフホステッド |
> |---|---|---|
> | 誰が用意するか | GitHub | **自社** |
> | 実行のたびに | **まっさらな状態から始まる** | **前回の状態が残ることがある** |
> | 入っているもの | よく使うツールが一式入っている | 自社で入れたものだけ |
>
> どちらの場合も **`actions/checkout` は必要**です。
> ただしセルフホステッドでは、**前回の実行で持ってきたファイルが残っている**ことがあります。
>
> だからこの演習では、いちばん上に**作業フォルダを空にする**ステップを入れていました。
> あれが無いと、前回の実行で取得した `README.md` がそのまま残っていて、
> **`actions/checkout` を書き忘れているのに成功してしまう**からです。
>
> これは実務でも起こります。
> 「checkout を書いていないのに、なぜか動いているワークフロー」は、
> セルフホステッド環境でよくある落とし穴です。
> そして**別のマシンで動かした瞬間に壊れます。**
> 「前回は動いたのに今日は失敗する」「隣の人は成功するのに自分は失敗する」の正体は、たいていこれです。

#### 直したコード

`ci.yml` を編集して、`- run: cat README.md` の**上に** checkout の行を足します。
**足すのは 1 行だけ**です。

```yaml
name: CI

on:
  push:

jobs:
  hello:
    runs-on: [self-hosted, Windows]
    steps:
      - name: 作業フォルダを空にする
        run: |
          Get-ChildItem -Force |
            Remove-Item -Recurse -Force -ErrorAction Ignore

      - uses: actions/checkout@v5

      - run: cat README.md
      - run: echo "done"
```

コミットして、`Actions` タブで **緑のチェック**になることを確認してください。

## 第 3 章 ハンズオン③ CI を成立させる

**Day 2 / 所要 15 分**

### この章のゴール

- ワークフローが **Pull Request でも動く**ようにする
- **テストを実行するステップ**を足す
- 実際に PR を作って、**PR 画面でチェックが走るのを見る**

### なぜこれをやるのか

Day 1 で作ったワークフローは、`push` のときにしか動きませんでした。
つまり、**すでに `main` に入ってしまった後**にしか気づけません。

CI（継続的インテグレーション）の本当の価値は、
**「`main` に入る前に止める」** ことにあります。

そのために必要なのが、**`pull_request` トリガー**です。

### 手順 3-1 自分のブランチで編集する

第 1 章からずっと、みなさんは**自分のブランチ**で作業してきました。
今回はそれを **`main` に取り込む** ところまでをやります。

**1.** `Code` タブ → `.github/workflows/ci.yml` を開き、**鉛筆マーク（✏️）** をクリックします。

> ⚠️ 左上のボタンが **`exercise/自分の名前`** になっていることを確認してください。

**2.** 中身を、**以下でまるごと置き換えてください。**
　　（`snippets/03-pr-test.yml` に同じ内容が入っています）

```yaml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: [self-hosted, Windows]
    steps:
      - uses: actions/checkout@v5
      - name: あいさつを表示する
        run: echo "Hello GitHub Actions"
      - run: ls
      - name: テストの代わり
        run: cat README.md
```

#### 変わったところ

| 変更点 | 意味 |
|---|---|
| `push:` に `branches: [ main ]` を追加 | `main` への push のときだけ動く。**自分のブランチへの push では動かなくなる** |
| **`pull_request:` を追加** | **PR が作られたとき／更新されたときにも動く** ← ここが今回の主役 |
| ジョブ名を `hello` → `test` に変更 | 役割がわかる名前にした |
| `- name: テストの代わり` を追加 | ステップに表示名を付けられる。ログが読みやすくなる |
| `run: cat README.md` | README.md があれば成功、無ければ失敗する（テストの代役） |

> **`npm test` や `mvn test` ではないのはなぜ？**
> このリポジトリには、まだアプリのコードもテストコードもありません。
> ここでは **「成功／失敗を判定するコマンドを置く場所」** を体験することが目的です。
> みなさんの実際のプロジェクトでは、この行が `npm test` や `mvn test` や `pytest` になります。

## 付録 B YAML の落とし穴

ワークフローファイルは **YAML** という形式で書きます。
プログラミング言語ではありませんが、**独特のルール**があります。

### ルール 1 字下げはスペース。タブは使えない

```yaml
# ❌ タブ文字は構文エラーになります
jobs:
→   build:

# ✅ 半角スペースを使います（2 個ずつが慣例）
jobs:
  build:
```

> ブラウザのエディタで打つぶんには、タブは入りにくいです。
> **他のファイルからコピーしたときに混入する**のが典型的なパターンです。

### ルール 2 字下げの深さが構造を決める

```yaml
# ❌ steps が jobs と同じ深さ → build ジョブの中身として認識されない
jobs:
  build:
    runs-on: [self-hosted, Windows]
steps:
  - run: echo hi

# ✅ steps は build の中なので、build より深く
jobs:
  build:
    runs-on: [self-hosted, Windows]
    steps:
      - run: echo hi
```

### ルール 3 コロンの後ろにはスペースが要る

```yaml
# ❌
name:CI

# ✅
name: CI
```

### ルール 4 `on` は予約語のように扱われる

`on:` は YAML では「真偽値の `true`」と解釈されることがある特殊な単語です。
GitHub Actions 側で正しく扱ってくれるので **そのまま `on:` と書いて問題ありません**が、
エディタによっては警告が出ることがあります。無視して構いません。

### ルール 5 `-` はリストの項目

```yaml
steps:
  - run: echo A     # 1 つめのステップ
  - run: echo B     # 2 つめのステップ
```

`-` を忘れると、2 つのステップが 1 つに混ざってエラーになります。

### 困ったときの確認手順

1. **`Code` タブでファイルを開く。** GitHub は YAML の構文エラーを画面上で赤く教えてくれます。
2. **Actions タブのエラーを見る。** `Invalid workflow file` と出ていたら、
   その下に **何行目が悪いか**が書いてあります。
3. **それでもわからなければ、この手順書のコードをまるごと貼り直す。** これが一番速いです。

## 付録 C 失敗パターン早見表

実務でよく出会う失敗と、その意味です。

| ログに出るメッセージ | 何が起きているか | どうすればいいか |
|---|---|---|
| `No such file or directory` | リポジトリのファイルが仮想マシンに無い | `actions/checkout` のステップを足す |
| `Invalid workflow file` | YAML の書き方が間違っている | エラーに出ている行番号を見て、付録 B を確認 |
| `command not found` | そのコマンドが仮想マシンに入っていない | セットアップ用の Action（`setup-node` など）を先に置く |
| `Process completed with exit code 1` | コマンドが失敗した（＝テストが落ちた等） | **その 1 つ上の行**に本当の原因が書いてある |
| `Resource not accessible by integration` | 権限が足りない | `permissions:` の設定を見直す（Day 2 で扱います） |
| `Error: Input required and not supplied` | Action に必須の入力を渡していない | その Action のドキュメントで `with:` を確認 |
| 実行がそもそも始まらない | トリガー条件に合っていない | `on:` の指定と、いま何をしたかを見比べる |
| `Waiting for a runner to pick up this job` が続く | ランナーの空きを待っている | しばらく待つ。数分続くなら講師に相談 |
| **自分の実行が見つからない** | 他の方の実行に埋もれている | `Code` タブの自分のブランチで、コミット横のマークをクリック |
| **編集しようとしたら怒られる** | `main` を編集しようとしている | 左上のボタンで `exercise/自分の名前` に切り替える |

### ログを読むときのコツ

**❌ が付いているステップだけを見てください。**
その上のステップは全部成功しています。読む必要はありません。

**エラー行の「1 つ上」に本当の原因があります。**
`exit code 1` は「失敗しました」という結果だけを言っています。
理由はその直前に出力されています。

## 付録 F 当日の進め方（お願い）

本日の環境では、**同時に実行できるワークフローが 1 つ**です。
全員が個別に実行すると、順番待ちだけで時間が過ぎてしまいます。

そこで演習は、**2 名 1 組**で進めていただきます。

| | やること |
|---|---|
| **操作役** | 画面を共有しながら、実際にコードを書いて実行します |
| **相談役** | 手順書を読み上げ、ログを一緒に読んで原因を考えます |

> **章ごとに役割を交代してください。** 3 回の演習があるので、
> どちらも操作する機会があります。
>
> ペアで進めることには、待ち時間を減らす以外の効果もあります。
> **ログを 2 人で読むと、1 人では気づかないことに気づけます。**
> 実際の開発でも、失敗したビルドのログは複数人で読むことが多いです。

#### ⚠️ 使うブランチは、ペアで 1 つです

第 0 章では**全員がそれぞれ自分のブランチを作ります**が、
**演習で実際に使うのは、ペアで決めた 1 つのブランチ**です。

**1.** ペアの最初に、**どちらのブランチを使うか**を決めてください。

**2.** **役割を交代しても、ブランチは変えません。**
　　交代した方は、リポジトリを開いて**同じブランチ**に切り替えてから操作します。

> **なぜ？**
> 3 回の演習は、**同じ 1 つのファイルを育てていく**構成です。
> 途中でブランチを変えると、それまでに書いたファイルが無い状態から始まってしまいます。

### 受講者側へのお願い

- **この手順書を開いたまま参加してください。** 印刷でも、別ウィンドウでも構いません。
- **できたら、チャットに「できました」と書いてください。** 全員の進み具合が講師に見えません。
- **詰まったら、すぐに声を上げてください。** 黙って詰まっているのがいちばんもったいないです。
- **エラーが出たら、チャットにメッセージを貼ってください。** テキストで貼っていただけると、
  講師がすぐに原因を特定できます。

### それでも進まなかったら

**大丈夫です。** 各章の最後に完成形のコードを載せてあります。
貼り替えれば、次の演習に参加できます。

**このワークショップの目的は、演習を完走することではありません。**
「Actions は、こう書いて、こう動いて、こう失敗する」という**感覚を持ち帰ること**が目的です。
